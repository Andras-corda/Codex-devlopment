5 · Backend & MVC

PHP utilisé pour ce qu'il fait depuis toujours : répondre à des requêtes HTTP, parler à une base de données, rendre du HTML. Le tout sans framework — juste PDO et une organisation MVC construite à la main.

Cycle requête → réponse

Plutôt qu'un fichier .php par URL, on fait passer toutes les requêtes par un point d'entrée unique (front controller) qui décide quoi faire selon l'URL demandée.

Superglobales

PHP expose la requête courante via des tableaux toujours accessibles, quelle que soit la portée (les seules variables qui échappent à la règle de portée par fonction).

SuperglobaleContient
$_GETparamètres de l'URL (?id=3)
$_POSTchamps d'un formulaire envoyé en POST
$_SERVERinfos sur la requête : REQUEST_URI, REQUEST_METHOD, en-têtes…
$_SESSIONdonnées persistées entre requêtes pour un même visiteur (après session_start())
$_COOKIEcookies envoyés par le navigateur
$_FILESfichiers envoyés via un formulaire multipart/form-data
Jamais de confiance aveugle

Tout ce qui vient de $_GET/$_POST/$_SERVER est écrit par l'utilisateur (ou un attaquant). On le valide avant de l'utiliser, on l'échappe avant de l'afficher (voir Sécurité), et on ne l'insère jamais directement dans une requête SQL (voir Requêtes préparées).

Formulaires

Un formulaire HTML envoie ses champs dans $_GET (méthode GET, visible dans l'URL — pour filtrer/rechercher) ou $_POST (méthode POST — pour créer/modifier/supprimer).

Champs à valeurs multiples

Des cases à cocher ou une liste à sélection multiple partageant le même name[] (avec des crochets) arrivent en PHP sous forme de tableau.

Valider et réafficher en cas d'erreur

Le motif classique : collecter les erreurs dans un tableau ; si vide, traiter ; sinon, réafficher le formulaire avec les valeurs déjà saisies (pour ne pas tout faire retaper) et les messages d'erreur.

Envoi de fichiers

Un formulaire qui envoie un fichier doit déclarer enctype="multipart/form-data" ; PHP le range dans $_FILES, jamais dans $_POST.

Ne jamais faire confiance à l'extension ni au type MIME envoyé par le navigateur

$fichier['type'] vient du navigateur et se falsifie facilement. Vérifier le contenu réel avec mime_content_type(), limiter la taille, et renommer le fichier à l'enregistrement plutôt que de garder le nom fourni par l'utilisateur.

Un formulaire qui modifie des données reste soumis à la même règle que partout ailleurs sur cette page : un jeton CSRF vérifié à la réception.

Routage minimal (front controller)

Tester en local

Le serveur intégré (php -S localhost:8000) ne réécrit pas les URL par défaut. Lui donner un script routeur : php -S localhost:8000 public/index.php fait passer chaque requête par le front controller, comme le ferait Apache/Nginx en production.

Se connecter à une base avec PDO

PDO (PHP Data Objects) est l'API native, orientée objet, pour parler à une base SQL — indépendante du moteur (MySQL, PostgreSQL, SQLite…).

Identifiants

Le mot de passe vient d'une variable d'environnement (getenv()), jamais codé en dur dans un fichier versionné.

Requêtes préparées — se protéger de l'injection SQL

Règle absolue

Une valeur venant de l'utilisateur n'est jamais concaténée dans une chaîne SQL. Toujours prepare() + execute([...]) — quel que soit le moteur ou la taille du projet.

Le pattern MVC

Modèle-Vue-Contrôleur sépare trois responsabilités qui, mélangées dans un seul script, deviennent vite illisibles.

CoucheResponsabilitéNe fait pas
Modèledonnées, règles métier, accès PDOne génère pas de HTML
Vueaffichage : transformer des données en HTMLne fait pas de requête SQL, ne décide rien
Contrôleurreçoit la requête, appelle le modèle, choisit la vuene contient pas de SQL, ni de HTML

Deux façons de l'implémenter : objet ou procédural

MVC est une idée de séparation des responsabilités, pas une syntaxe imposée. On peut l'appliquer avec des classes (la version détaillée plus bas) ou avec de simples fonctions et fichiers inclus — la version qu'on trouve dans beaucoup de petits sites PHP, souvent plus rapide à lire d'un bout à l'autre pour un projet modeste.

Version procédurale (sans classes)

Le routage se fait sur l'URL elle-même (pas un paramètre ?page=), avec des fonctions de contrôleur groupées par domaine — proche de ce que fait un projet réel sans framework : un index.php minimal, un contrôleur central qui route et délègue, des modèles qui n'exposent que des fonctions.

Le gabarit à trou : la vraie astuce de ce style

require partage la portée locale du fichier appelant. Le contrôleur pose $template (un chemin de fichier) puis require vues/base.php ; celui-ci fait à son tour require $template; exactement là où il veut insérer le contenu. Résultat : un layout unique (en-tête, pied de page, CSS) partagé par toutes les pages, sans classe ni moteur de template — juste deux require imbriqués.

Le choix « try/catch + valeur de repli » a un coût

Chaque fonction modèle avale l'exception et journalise avec error_log() : la page ne plante jamais sur un souci de base de données, mais l'appelant ne sait pas qu'une erreur a eu lieu — seuls les logs le disent. C'est un compromis délibéré pour un site public ; la version objet ci-dessous laisse l'exception remonter, à charge pour un point unique de l'attraper.

Laquelle choisir ?

Les deux sont légitimes. Commencer en procédural pour un script ou un petit site ; basculer vers l'objet quand les routes, les modèles ou les variantes de vue se multiplient et que la duplication devient pénible à maintenir.

Version orientée objet

C'est celle détaillée dans les trois sections qui suivent (Le Modèle, La Vue, Le Contrôleur) : mêmes responsabilités que ci-dessus, mais chaque couche est une classe qu'on peut étendre, remplacer par injection, ou tester isolément avec un faux PDO.

La Vue

Un gabarit PHP simple : du HTML avec quelques échappatoires <?= ?> pour insérer des données — toujours échappées.

XSS

Toute donnée affichée dans une vue passe par htmlspecialchars($valeur, ENT_QUOTES) (ou une fonction d'échappement équivalente) — sinon un titre d'article contenant <script> s'exécute dans le navigateur des autres visiteurs.
