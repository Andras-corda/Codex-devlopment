4 · Levels & Game Framework

Organiser un projet : quelles règles s'appliquent où (Game Mode), quelles données survivent aux changements de niveau (Game Instance), et comment découper le monde (niveaux & sublevels).

Game Mode

Le GameMode définit les règles de la partie pour le niveau courant : quelle classe de Pawn faire spawn (Default Pawn Class), quel PlayerController, quel HUD, quel GameState. Il n'existe que sur le serveur (en multijoueur) — les clients n'y ont pas d'accès direct.

ClasseRôle
GameModeBaserègles du jeu, spawn du joueur — un par niveau chargé
GameStateBasedonnées de partie répliquées à tous les clients (score, timer)
PlayerControllerreprésente un joueur (humain), gère l'input et la caméra
Pawn / Characterl'avatar physique contrôlé dans le monde

Un Blueprint dérivé de GameModeBase fixe les classes par défaut utilisées pour chaque joueur qui rejoint la partie :

Classe par défautRôle
Default Pawn Classle Pawn/Character spawné pour le joueur, à l'emplacement d'un PlayerStart (voir aussi Pawn & possession)
HUD Classl'interface affichée à l'écran
PlayerController Classle contrôleur qui reçoit l'input du joueur
Spectator ClassPawn utilisé en mode spectateur

Un GameMode par niveau

L'override par niveau prend le pas sur le défaut du projet — utile pour un menu (pas de personnage) vs un niveau de jeu (personnage 3e personne).

Game State (& Player State)

Le GameMode n'existe que sur le serveur ; le GameState, lui, existe sur le serveur et est répliqué à tous les clients — c'est l'endroit pour tout ce que tous les joueurs doivent voir : liste des joueurs connectés, score d'équipe, temps de jeu écoulé, la partie a-t-elle commencé.

PortéeExemple
GameStateun par partie, visible de tousscore de l'équipe, chrono, missions accomplies
PlayerStateun par joueur, visible de tousnom du joueur, son propre score/kills
GameState vs PlayerState

Une donnée qui appartient à un joueur en particulier (mais que les autres doivent quand même voir, ex. le score individuel dans un match en équipe) va dans PlayerState, pas dans GameState — ce dernier ne suit que ce qui est global à la partie. Ces deux notions n'ont vraiment d'importance qu'en multijoueur (répliqué réseau) ; en solo, une variable de GameInstance suffit souvent.

PlayerStart & apparition du joueur

Un PlayerStart est un Actor posé dans le niveau (une capsule verte avec une flèche : la capsule donne la taille du joueur, la flèche son orientation au spawn). Il marque où un joueur apparaît ; le GameMode en choisit un à chaque fois qu'il doit créer ou recréer un Pawn.

SituationComportement
Plusieurs PlayerStartChoose Player Start prend l'un de ceux qui ne sont pas obstrués, au hasard — aucun ordre garanti
Aucun PlayerStartle joueur apparaît à l'origine du monde (0, 0, 0), avec un avertissement dans le log
Champ Player Start Tagun nom libre sur chaque PlayerStart, pour les distinguer (checkpoint, équipe, entrée de zone)
Play From Herel'éditeur crée un PlayerStartPIE temporaire à l'endroit choisi, sans toucher à ceux du niveau

Respawn & choix personnalisé

Nœud (GameMode)Rôle

Mort & respawn

À la mort : UnPossess puis détruire (ou laisser en ragdoll) l'ancien Pawn, puis Restart Player. Appeler Restart Player sans nettoyer l'ancien Pawn laisse un cadavre inerte dans le niveau et peut dupliquer le personnage.

Checkpoints

Poser plusieurs PlayerStart avec des Player Start Tag différents. Un trigger de checkpoint écrit son tag dans la GameInstance (et dans un SaveGame pour survivre à la fermeture). Dans le Choose Player Start surchargé : Get All Actors of Class (PlayerStart), boucle, renvoyer celui dont le tag correspond — sinon le premier de la liste.

Game Instance

Contrairement au GameMode (recréé à chaque changement de niveau), la GameInstance est créée une seule fois au lancement du jeu et survit à tous les chargements de niveaux — l'endroit naturel pour des données globales (inventaire, score total, préférences, état de sauvegarde).

Durée de vie
GameInstancetoute la session de jeu, à travers tous les niveaux
GameMode / GameStaterecréé à chaque changement de niveau
PlayerControllerpersiste tant que le joueur reste connecté (peut survivre à un changement de niveau « seamless »)

Sauvegarder la partie (SaveGame)

Une GameInstance vit le temps d'une session — elle ne survit pas à la fermeture du jeu. Pour persister des données entre deux sessions (sur le disque), Unreal fournit les SaveGame : une classe Blueprint dérivée de SaveGameObject, qui ne contient que des données (comme une Structure), sérialisées automatiquement.

ÉtapeNœud / élément
1. Définir le contenucréer un Blueprint BP_SaveGame (parent SaveGame) avec les variables à conserver (score, position, inventaire…)
2. Créer une sauvegardeCreate Save Game Object (classe = BP_SaveGame), remplir ses variables, puis Save Game to Slot (nom de slot + index utilisateur)
3. ChargerDoes Save Game Exist (le slot existe-t-il ?) puis Load Game from Slot → cast vers BP_SaveGame pour relire ses variables
4. SupprimerDelete Game in Slot
Que mettre dans un SaveGame

Uniquement des données (nombres, texte, structures, tableaux) — jamais une référence directe à un Actor du niveau (il n'existera plus au prochain lancement). Pour restaurer une position ou un inventaire, sauvegarder les valeurs puis reconstruire/repositionner les Actors correspondants au chargement.

Où garder la référence

La GameInstance est l'endroit naturel pour garder l'objet SaveGame chargé en mémoire : elle survit aux changements de niveau, contrairement au GameMode.

Levels & Sublevels

Un projet Unreal découpe son monde en niveaux (fichiers .umap). Un Persistent Level peut charger d'autres niveaux comme sublevels, chargés/déchargés à la volée (streaming) — utile pour un monde ouvert ou pour séparer l'éclairage/l'architecture du gameplay. Quand et comment un sublevel se charge dépend de sa méthode de streaming.

MécanismeRôle
Load Stream Level / Unload Stream Levelcharge/décharge un sublevel depuis un Blueprint (ex. au passage d'un trigger)
Level Streaming Volumecharge automatiquement un sublevel quand la caméra entre dans son volume
Level Blueprintgraphe d'évènements propre à un seul niveau — voir plus bas

Changer complètement de niveau : Open Level

Le streaming ci-dessus ajoute des sublevels par-dessus le Persistent Level. Pour tout remplacer (quitter un niveau de jeu vers le menu principal, passer au niveau suivant), Open Level décharge tout et charge un niveau entièrement neuf.

Effetdécharge tout, recharge un niveau neufajoute/retire des sublevels sur le Persistent Level en cours
GameModerecrééinchangé

Bon pourmenu ↔ niveau de jeu, niveau suivantmonde ouvert, zones d'un même niveau

Méthodes de streaming

Un sublevel s'ajoute depuis la fenêtre Levels (Window → Levels, menu Levels → Add Existing… ou Create New…) et on lui attribue une méthode de streaming (clic droit sur le niveau → Change Streaming Method). Elle décide quand il est en mémoire.

MéthodeChargé quandPiloté parBon pour
Always Loadedavec le Persistent Level, toujours visiblerien : automatiquedécouper le travail (éclairage, audio, gameplay, décor) sans rien changer à ce que voit le joueur
Blueprintà la demandeLoad Stream Level / Unload Stream Level, ou des Level Streaming Volumeszones qui apparaissent et disparaissent : intérieurs, chapitres, donjons
Level Streaming Volumequand la caméra entre dans le volumeun volume posé dans le niveau, lié au sublevel (Level Details → Streaming Volumes)streaming sans script, sur des zones fixes
World Composition (hérité, UE4)selon la distance à la tuileréglage de distance par tuilegrands mondes de l'ancienne génération — remplacé par World Partition
World Partition (UE5)cellules d'une grille autour du joueurgrille runtime (taille de cellule, Loading Range) et Data Layersmonde ouvert : plus de sublevels à découper à la main

Piloter un sublevel depuis un Blueprint

NœudRôle
Load Stream Level (by Name / by Object Reference)charge un sublevel déjà présent dans la fenêtre Levels. Make Visible After Load : l'affiche dès qu'il est prêt ; décoché, il se charge mais reste caché (précharger pendant un écran de transition). Should Block on Load : fige le jeu jusqu'à la fin du chargement
Unload Stream Leveldécharge le sublevel et détruit tous ses Actors (Should Block on Unload disponible)

Set Data Layer Runtime State (World Partition)fait passer une Data Layer de Unloaded à Loaded puis Activated — l'équivalent de Load/Unload pour un monde World Partition
Ce qui disparaît avec le sublevel

Décharger un sublevel détruit ses Actors et leur état : une porte ouverte, un coffre vidé repartent de zéro au prochain chargement. Sauvegarder l'état dans la GameInstance ou un SaveGame. Éviter aussi les références directes d'un sublevel à l'autre : déchargé, l'autre bout devient None (Accessed None) — passer par un Event Dispatcher ou chercher l'Actor au chargement.

Quelle méthode choisir

Petit niveau, tout tient en mémoire : Always Loaded (juste pour s'organiser). Zones bien délimitées (bâtiments, chapitres) : Blueprint avec trigger ou volume. Monde ouvert continu sous UE5 : World Partition — dans un tel monde on ne découpe plus en sublevels, l'éditeur range les Actors en cellules, et les Data Layers servent à activer ou non des couches entières.

Level Blueprint

Chaque niveau (.umap) possède un Level Blueprint unique, ouvert depuis la barre d'outils (Blueprints → Open Level Blueprint). C'est un Event Graph attaché au niveau lui-même : il n'a pas de composants, n'est pas instanciable, et ne peut pas être réutilisé ailleurs. Chaque sublevel a le sien, en plus de celui du Persistent Level.

Ce qu'il sait faireComment
Référencer un Actor posé dans le niveausélectionner l'Actor dans le viewport, puis clic droit dans le graphe → Create a Reference to … — sans Get All Actors of Class
Réagir aux événements de cet ActorActor sélectionné → clic droit → Add Event for … (ex. OnActorBeginOverlap d'un Trigger Box)
Scénariser le niveaulancer une cinématique (Level Sequence), ouvrir une porte, faire apparaître des ennemis, changer la musique
Gérer le streamingLoad Stream Level / Unload Stream Level au passage d'un trigger
Les limites du Level Blueprint

Aucun autre Blueprint ne peut obtenir de référence vers lui : un personnage ou un widget ne peut pas l'appeler directement. La communication se fait dans l'autre sens — le Level Blueprint s'abonne aux Event Dispatchers des Actors qu'il référence. Et toute logique qui pourrait servir dans deux niveaux (porte, interrupteur, coffre) doit vivre dans un Actor Blueprint réutilisable, pas dans le Level Blueprint.

Où mettre la logique ?
Level Blueprintévénements uniques à ce niveau : cinématique d'intro, piège scripté, streaming
Actor Blueprinttout objet qui se répète : porte, levier, ennemi, pickup
GameModerègles de la partie : conditions de victoire, respawn
GameInstancedonnées qui traversent les niveaux
