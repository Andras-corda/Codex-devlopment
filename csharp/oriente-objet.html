On modélise le problème avec des objets : chacun réunit un état (des données) et un comportement (des méthodes) cohérents.

Classe & objet

Une classe est un plan. Un objet est une réalisation concrète de ce plan, créée avec new. Une classe, mille objets.

Champs, propriétés et accesseurs get / set

Un champ (field) est une variable stockée dans l'objet. Une propriété (property) est une paire d'accesseurs — get pour lire, set pour écrire — qui s'utilise comme un champ mais laisse ajouter validation, calcul ou journalisation. Dans un set, le mot-clé value désigne la valeur affectée.

Champs readonly & constantes

Trois façons de figer une valeur, de la plus stricte à la plus souple :

Mot-cléFixée…Portée
constà la compilation (littéral obligatoire)une valeur, implicitement static ; copiée dans le code appelant
static readonlyau chargement du type (peut être un calcul, un new)une valeur par type
readonly (champ d'instance)dans le constructeurune valeur par objet, immuable ensuite
readonly n'est pas une immuabilité profonde

private readonly List<int> _items; empêche de réaffecter _items, mais pas d'appeler _items.Add(3). Pour un objet vraiment gelé : propriétés init, record, ou ImmutableArray<T>.

Sur un type valeur : readonly struct gèle tout le type, et readonly sur une méthode de struct garantit qu'elle ne modifie pas l'instance. Voir Structures.

Membres statiques

Un membre static appartient au type, pas à une instance : il existe en un seul exemplaire, partagé, et s'appelle via le nom du type. Un membre d'instance appartient à chaque objet.

À manier avec prudence

Un champ static mutable est une variable globale : état partagé, difficile à tester, source de bugs en contexte multithread. Réserver static aux constantes, aux fonctions pures (Math.Sqrt) et aux fabriques.

Héritage

Une classe dérivée est un cas particulier de sa classe de base : elle hérite de ses membres et peut en ajouter ou en redéfinir.

Règles

C# n'a pas d'héritage multiple de classes (une seule base). sealed class interdit d'hériter. Sans virtual (ou abstract) sur le parent, pas d'override possible.

Polymorphisme

Un même appel, exécuté différemment selon le type réel de l'objet — décidé à l'exécution.

Interfaces en détail

Une interface est un contrat : la liste des membres qu'un type s'engage à fournir. Elle dit ce qu'un objet sait faire, jamais comment. Convention : le nom commence par I. Ses membres sont implicitement public et elle ne contient pas d'état d'instance.

  • une classe (ou un struct) peut implémenter plusieurs interfaces ;
  • on déclare les variables du type de l'interface → l'implémentation devient interchangeable ;
  • depuis C# 8, une interface peut fournir une implémentation par défaut.

Structures (struct)

Un struct est un type valeur : il contient directement ses données (pas de référence), il est copié à chaque affectation ou passage en paramètre, et il vit en général sur la pile ou à l'intérieur de l'objet qui le contient. À réserver aux petites valeurs sans identité : un point, une couleur, un montant, une plage de dates.

Piège du type valeur

Modifier un struct renvoyé par une propriété ou lu dans une liste modifie une copie, silencieusement. Bonne pratique : readonly struct + propriétés init → immuable, aucune surprise.

record — données par valeur

Un record est une classe que le compilateur outille pour représenter une donnée : égalité par valeur, ToString() lisible, copie non destructive avec with, immuabilité par défaut.

global using & global::

Deux usages distincts du mot-clé global.

global using — importer un espace de noms dans tout le projet

Un global using vaut pour tous les fichiers du projet : on le déclare une seule fois, en général dans un fichier dédié (GlobalUsings.cs).

ImplicitUsings

Avec <ImplicitUsings>enable</ImplicitUsings> dans le .csproj, le SDK génère déjà des global using pour les espaces de noms courants (System, System.Linq, System.Collections.Generic…). C'est pourquoi les exemples de ce guide n'ont aucun using.

global:: — lever une ambiguïté de nom

Le préfixe global:: force la résolution depuis la racine des espaces de noms, utile quand un nom local masque un type de la bibliothèque.

Composition plutôt qu'héritage

Souvent, « a un » vaut mieux que « est un » : au lieu d'hériter, on contient un objet qui fait le travail. Plus souple, moins fragile.
