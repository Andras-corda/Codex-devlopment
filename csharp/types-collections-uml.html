Rédiger de l'UML — la boîte de classe

Un diagramme de classes communique la structure d'un modèle : les types, leurs membres visibles, et surtout leurs relations. On y met ce qui aide à comprendre, pas chaque détail du code.

  • N'affichez que les membres utiles au lecteur — souvent la partie public et les champs qui portent une relation.
  • Les propriétés C# se notent comme des attributs (pas besoin de montrer get/set).
  • Un «stereotype» au-dessus du nom précise la nature : «interface», «enumeration», «record», «abstract».

Composition ou agrégation ?

Posez la question : « si je détruis le tout, la partie a-t-elle encore un sens ? » Une Facture et ses LigneFacture → composition. Une Equipe et ses Joueur → agrégation (le joueur existe sans l'équipe). En pratique, beaucoup de gens ne distinguent que composition vs association.

Conseils de rédaction

  • Un diagramme = une intention. « Vue d'ensemble du domaine », « le sous-système de paiement »… pas « toutes les classes ».
  • Omettez le bruit : getters/setters triviaux, constructeurs, ToString, classes techniques (DTO, helpers).
  • Nommez les extrémités quand ce n'est pas évident : rôle (employeur/employé) et multiplicité (1, *).
  • Le sens des flèches compte : dessinez la navigation réelle (qui référence qui).
  • Préférez la composition à l'héritage dans le modèle — et le diagramme le montrera.
  • Gardez-le vivant : un diagramme faux est pire qu'aucun. Le texte (Mermaid/PlantUML) versionné avec le code vieillit mieux qu'une image.
