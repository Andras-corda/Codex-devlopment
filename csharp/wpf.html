5 · WPF

Windows Presentation Foundation : le framework d'interface graphique de bureau de .NET. Interfaces décrites en XAML, logique en C#, et un pattern d'architecture qui revient partout : MVVM.

Qu'est-ce que WPF

WPF sépare structurellement ce qu'on voit (le XAML, un langage à balises déclaratif) de ce qui se passe (le C#, dans un fichier « code-behind »). Windows uniquement, mais toujours d'actualité pour des applications de bureau riches (outils internes, logiciels métier).

Bases de XAML

XAML est du XML : chaque balise est une classe .NET, chaque attribut une propriété. Un élément enfant devient une propriété de contenu ou de collection du parent.

Équivalent en C# (ce que le compilateur génère en coulisses) — comprendre ça aide à démystifier le XAML :

x:Name vs Name

x:Name="MonBouton" donne un nom à un élément pour y accéder depuis le code-behind (MonBouton.Content = "...") — le compilateur génère un champ correspondant automatiquement.

Événements

En XAML, un attribut d'événement (Click, TextChanged…) référence une méthode du code-behind. Sous le capot, c'est exactement le mécanisme délégué / event vu en Procédural.

Code-behind : à utiliser avec parcimonie

Gérer chaque bouton directement dans MainWindow.xaml.cs fonctionne pour un prototype, mais mélange vite affichage et logique métier. Le pattern MVVM ci-dessous règle ce problème.

Liaison de données (data binding)

Plutôt que de lire/écrire manuellement chaque contrôle, on lie une propriété XAML à une propriété C#. WPF synchronise automatiquement dans les deux sens.

Pour que le second contrôle se mette à jour quand le premier change, la classe source doit prévenir WPF via INotifyPropertyChanged :

DataContext

DataContext est l'objet contre lequel tous les {Binding} d'un élément (et de ses enfants, par héritage) se résolvent. Le fixer une fois sur la fenêtre suffit pour tous ses contrôles.

Le pattern MVVM

Model-View-ViewModel : la variante de MVC pensée pour le data binding. La Vue ne connaît que des liaisons ; le ViewModel expose des propriétés observables ; le Modèle reste la donnée et les règles métier.

CoucheResponsabilitéNe fait pas
Modeldonnées, règles métierne sait rien de l'affichage
ViewModelpropriétés observables, commandes, logique de présentationne référence aucun contrôle XAML
ViewXAML + bindingsidéalement zéro logique dans le code-behind

Commandes (ICommand)

L'équivalent MVVM d'un gestionnaire d'événement : un bouton se lie à une commande plutôt qu'à une méthode Click, ce qui garde toute la logique dans le ViewModel.

CanExecute désactive le bouton automatiquement

Quand CanExecute renvoie false, WPF grise le contrôle lié — inutile de gérer IsEnabled à la main.

Styles & ressources

Un Style regroupe des valeurs de propriétés réutilisables ; une ResourceDictionary les rend disponibles à toute une fenêtre (ou toute l'application, depuis App.xaml).

Convertisseurs de valeur

Un IValueConverter transforme la valeur liée entre le ViewModel et l'affichage (ex. bool → Visibility).

Navigation entre fenêtres

Pour une navigation « en place » dans une seule fenêtre (comme des onglets successifs), on utilise un Frame qui affiche des Page plutôt que des Window séparées.
